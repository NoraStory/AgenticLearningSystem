# CodeForge Academy — 完整后端系统实现计划

## Summary

基于用户提供的 Next.js 16 前端项目(含 API_SPEC.md / DATABASE_DESIGN.md / AGENT_DESIGN.md 三份完整文档),实现完整的后端系统。后端语言选 **Go**(高并发原生支持、单二进制部署、goroutine 并行 Agent)。融合现有 Python 系统中有价值的组件(rustc 代码检测引擎、代码注入式 tracer、AI prompt 模板)作为 Go 调用的外部工具。实现 MinIO 对象存储、沙箱自修复、Tool 插件系统、多 Agent Harness(并行互不干涉)。

## 核心架构

```
Next.js 前端 (:5000)  ──→  Go 后端 (:8080)  ──→  PostgreSQL (5432)
                               ├──→  Redis (6379, 缓存/会话)
                               ├──→  MinIO (9000/9001, 对象存储)
                               ├──→  Python 检测引擎 (子进程, rustc/cargo/tracer)
                               ├──→  AI Agent Harness (并行子Agent)
                               └──→  Tool 插件层 (联网搜索/代码执行/课程检索)
```

## 关键技术决策

- **后端语言: Go 1.26** — goroutine 天然高并发,单二进制部署,`net/http` 内置高性能
- **数据库: PostgreSQL** — 按文档设计,11 张表,含 pgvector 扩展
- **缓存: Redis** — 会话/排行榜/每日一题/进度缓存
- **对象存储: MinIO** — 代码提交快照、用户头像、课程封面图、AI 对话记录
- **代码检测: 保留现有 Python checker/tracer** — Go 通过 subprocess 调用,利用已验证的 rustc + sccache + 代码注入方案
- **AI 后端: 火山方舟 Ark API** (glm-5-2-260617) — 沿用现有配置
- **沙箱: Windows 受限令牌进程** — Go 用 `syscall` 创建受限令牌子进程(无网络/无文件写入/有CPU+内存限制),替代 CubaSandBox(无 Windows 原生支持)

## 实现分块

### 1. Go 后端核心 (Gin/Fiber + GORM)

- `cmd/server/main.go` — 入口,初始化 DB/Redis/MinIO/Agent
- `internal/config/` — 配置(.env: DB/Redis/MinIO/Ark API)
- `internal/model/` — GORM 模型(11 张表,对应 DATABASE_DESIGN.md)
- `internal/handler/` — HTTP handler(对应 API_SPEC.md 全部接口)
- `internal/middleware/` — JWT 认证/CORS/限流/日志
- `internal/service/` — 业务逻辑层

### 3. 代码执行与自修复沙箱

- `internal/sandbox/` — Windows 受限令牌沙箱:
  - `CreateRestrictedToken()` 创建受限令牌
  - `CreateProcessAsUser()` 用受限令牌启动子进程
  - 限制:无网络访问、只能写入临时目录、CPU 时间限制 30s、内存限制 256MB
  - 使用 Job Object 管理进程组,确保子进程不会逃逸
- `internal/checker/` — 调用现有 Python checker.py(trustc/cargo 编译运行 + 输出比对)
- **自修复流程**:
  1. 用户提交代码 → 编译失败 → 捕获 stderr
  2. 将代码 + 错误信息送入沙箱(受限进程)
  3. AI Agent 分析错误 → 生成修复方案
  4. 在沙箱内应用修复 → 重新编译验证
  5. 编译通过 → 合并到用户代码(用户可预览 diff 后确认)
  6. 编译失败 → 返回错误,不合并

### 4. Tool 插件系统

每个 Tool 是独立模块,前端可单独启用/禁用:
- `internal/tools/registry.go` — Tool 注册表 + 启用/禁用状态管理
- `internal/tools/search.go` — **联网搜索 Tool**(调用搜索 API,返回结果给 Agent)
- `internal/tools/code_exec.go` — **代码执行 Tool**(调用沙箱编译运行)
- `internal/tools/course_search.go` — **课程检索 Tool**(PostgreSQL FTS)
- `internal/tools/progress_query.go` — **进度查询 Tool**
- `internal/tools/trace_debug.go` — **逐步调试 Tool**(调用 Python tracer)
- Tool 接口: `type Tool interface { Name() string; Execute(ctx, params) (result, error) }`
- 前端 `POST /api/v1/agent/tools` 控制启用/禁用,Agent 只调用已启用的 Tool

### 5. 多 Agent Harness (并行互不干涉)

参考 Claude Code / OpenCode 的并行 Agent 模式:
- `internal/harness/orchestrator.go` — 主编排器,管理子 Agent 生命周期
- **三个子 Agent**(按 AGENT_DESIGN.md):
  - `learning_assistant` — 学习助手(RAG 检索 + 上下文管理)
  - `code_reviewer` — 代码审查(代码分析 + 优化建议)
  - `problem_tutor` — 题目讲解(思路引导 + 示例代码)
- **并行机制**:
  - 每个 Agent 运行在独立 goroutine 中
  - 每个 Agent 有独立的 context.Context(超时/取消独立)
  - 共享状态通过 channel 传递(非共享内存)
  - 每个 Agent 有独立的 AI 对话历史(存储在 Redis,按 agent_type + user_id 隔离)
  - Tool 调用通过 Tool 注册表串行化(避免并发写冲突)
- `internal/harness/scheduler.go` — 调度器,决定何时启动哪个 Agent(可并行启动多个)

### 6. MinIO 对象存储

- 代码提交快照:`submissions/{user_id}/{problem_id}/{timestamp}.rs`

- 课程封面图:`courses/{course_id}.jpg`

## Assumptions

- **后端语言选 Go**: 用户说"自行选择",Go 在高并发(goroutine)、单二进制部署、Windows 原生支持上优于 Python;现有 Python checker/tracer 作为子进程调用不影响性能

- **前端端口**: Next.js 在 :5000(Coze 配置),后端 API 在 :8080,CORS 已配置
